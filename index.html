Zero Code Changes

The router sits transparently between clients and backends. Clients send requests to port 8899 using standard OpenAI-compatible APIs.

Envoy's External Processing filter (ExtProc) intercepts each request via gRPC, classifies it, and routes to the right model.

Clients always send model: "auto". The router selects the actual backend transparently.

Priority-Based Evaluation

Decisions are evaluated highest priority first. The first matching rule wins. Safety rules at P90+ always fire before routing decisions.

Every response includes x-vsr-* headers for full observability. You can see exactly which decision fired and why.

The DSL compiles human-readable rules into optimized YAML, Kubernetes CRDs, or Helm values.

Fine-Tuning the Router

The pretrained embedding model (all-MiniLM-L6-v2) achieves only 80.4% accuracy for complexity-tier classification.

Using BatchAllTripletLoss with synthetic data generation, we pushed accuracy to 98.5%. A +18% improvement with just 805 training examples.

For telecom and enterprise workloads, accurate routing means 86% of requests stay on free local models.

Fine-Tuning the Router for Production

Pretrained embeddings misroute 1 in 5 requests. Fine-tuning with synthetic data and contrastive learning closes that gap.

  • ›The problem: all-MiniLM-L6-v2 achieves only 80.4% accuracy on 4-tier complexity classification (SIMPLE / MEDIUM / COMPLEX / REASONING)MEDIUM tier recall was just 62.5%
  • ›Synthetic data generation: 805 training examples from 48 seed anchors using 6 strategiesparaphrase, domain transfer, boundary cases, hard negatives, real-world patterns, and perturbation
  • ›Key breakthrough: switching from MNRL to BatchAllTripletLoss with GROUP_BY_LABEL batch samplingforces the model to learn every tier boundary in every batch
  • ›Result: 98.5% accuracyonly 3 errors in 204 tests, all at the genuinely ambiguous MEDIUM/COMPLEX boundary. Misrouting rate dropped from 19.6% to 1.5%
  • ›Production path: 23M parameter model fine-tunes in under 2 hours on CPU. Drops into the router as a model swapno architecture changes, no redeployment

Why This Matters

Accurate routing is the foundation for every use case: cost optimization only works if requests actually land on the right model.

Even with fine-tuning, routing is layer one of defense in depthguardrails and egress controls must still backstop misclassifications.

Loss function selection mattered more than data volume: +18% from the right loss vs. +2% from more data.

LLM-d: Production Inference Stack

Semantic Router decides which model handles a request. LLM-d optimizes how that model runs.

What LLM-d Does
  • ›KV-cache-aware schedulingroutes requests to the pod whose cache already holds the matching prefix
  • ›Prefix-hash routingsimilar prompts always land on the same worker, maximizing cache reuse
  • ›Tiered memory offloadingspills KV-cache from GPU → CPU → storage, keeping hot entries on-device
  • ›Continuous batchingvLLM serves requests with PagedAttention and tensor parallelism for high throughput
Kubernetes-Native Deployment
  • ›IntelligentPool CRDdefines model backends with capabilities, pricing, and endpoints as K8s resources
  • ›IntelligentRoute CRDdeclares routing rules, signal configs, and decision policies as custom resources
  • ›Helm + HPAone-command deployment with auto-scaling; router scales independently from backends
  • ›OpenShift readyGPU scheduling, multi-cluster federation, hybrid cloud orchestration out of the box

Two Layers, One Stack

The Semantic Router handles the "what". Content classification, policy enforcement, model selection.

LLM-d handles the "how". KV-cache indexing, prefix-hash routing, GPU/CPU/storage tiering for maximum throughput.

Deploy anywhere, route intelligently, serve efficiently.
